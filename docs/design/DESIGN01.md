## Header
- Date: 2026-11-18

## Problem
Парсер работает на честном слове и нечитаемом коде. в ветке main он существует в виде очень странного, но рабочего модуля, а попытки его переписать в ветке refactor/eql не увенчались успехом, в частности из за того что прежде чем писать столь критичный компонент надо думать головой. с целью вывода мыслей и решения в человекочитаемый вид был создан данный документ, ознаменовавший вообще начало недо-дизайн-доков в проекте. Что нужно - Рабочий парсер, который вернет из себя еденицу процессинга, которая будет готова к обработке процессором и не будет нуждатся в дополнительном парсинге. Линковка имени типов с их айди допустима.

## Don't Including
В этой конкретной задаче не предусматривается работа парсера со скобками, в т.ч вложенными, Предусматривается только работа с текущим Tokens что дает нам лексер, без добавления новых вариантов в процессе, и не предусматривается работа над процессором. Процессор будет собиратся на том, что получится из парсера. Также приоритеты логических операторов, их вложенность и т.д будут добавленны когда заработает то что описано тут.

## Solve
Парсер должен принимать на вход массив токенов, а на выходе давать массив едениц обработки   

Еденица обработки - какая то структура, содержащая данные, которые будут использованны процессором для получения результата (и в будущем установки значений) из мира (структура World в ECS). Еденицу обработки стоит представить как enum ProcessingUnit, содержащий в вариантах типы едениц обработки. на данный момент это только SelectingUnit. по идее, вариант SelectingUnit будет выбиратся когда у нас стоит токен SELECT в начале, назовем его Unit Assign Token (UAT). таким в будущем может стать SET и прочее, но пока что будем строить на том что есть. Вместо скобок как в прошлых версиях, ознаменовывать начало и конец юнита будут именно UAT. SelectingUnit будет содержать некоторые данные, необходимые для выбора нужных сущностей из World.  

Назовем их филтры. Фильтр - это набор каких то характеристик, которые должны быть у сущности, чтобы она попала в результат работы процессора. сейчас у нас есть 4 токена, отвечающих за такое. With, Without, And, Or. первые два самостоятельные. они говорят о том, какие параметры (на данный момент это Компоненты) должны быть у сущности, чтобы та попала в выборку. последние два - это логические операторы, которые должны ставится между двумя токенами With/Without, и обозначают следующее: And - сущность должна относится и к левому, и к правому фильтру. например ```WITH Position AND WITHOUT Dead``` обработается как Сущности, которые есть в выборке WITH Position и есть в выборке WITHOUT Dead.  

Как можно представить фильтры. Допустим это будет enum Filter. Каждый фильтр мы назовем одноименно токену, который относится к нему. всего получится четыре фильтра. Токены сами по себе данных не содержат, а филтры будут. примерная структура такова:
```rust
enum Filter {
    With(Vec<String>),
    Without(Vec<String>),
    And { a: Box<Filter>, b: Box<Filter> },
    Or { a: Box<Filter>, b: Box<Filter> },
}
```
Первые два содержат в себе массив строк, которые обозначают типы. Например из запроса ```WITH Position Velocity Rotation``` получится ```Filter::With(["Position", "Velocity", "Rotation"])```. Все эти имена должны превращатся в TypeId на этапе линковке в модуле процессора. Не в парсере, потому как он еще не должен зависеть от ECS.  

Вторые два фильтра содержат в себе другие фильтры, а именно With и Without (хотя по идее туда поместятся и And с Or, но это не то о чем сейчас нужно думать).  

Итак, имея некие фильтры, которые говорят что нужно выбирать, мы можем добавить их в наш SelectingUnit. и вот как на данном этапе может выглядеть ProcessingUnit:
```rust
enum ProcessingUnit {
    SelectingUnit {
        filters: Vec<Filter>
    }
}
```
Разберем подробнее обработку фильтров. скорее всего потребуется два этапа разбора. первый, когда мы просто преобразуем токены в сырые фильтры With, Without и пустые And, Or, и второй, когда получившиеся фильтры мы слепляем в And и Or. то есть, допустим у нас есть набор токенов ```[With, Type(..), Type(..), And, Without, Type(..)]```, первый шаг даст нам фильтры ```[With("Type1", "Type2"), And, Wihout("Type3")]``` а второй склеит это в ```[And(With("Type1", "Type2"), Wihout("Type3"))]```. Забегая вперед, потом в процессоре мы просто просто проходимся по таким Фильтрам, получаем сначала два массива сущеностей из этих With/Without, а затем применяем intersection. Также парсер будет расставлять логические операторы And между двумя With(out). то есть, можно написать ```WITH Position WITHOUT Dead```, а парсер автоматически подставит туда And, и получится как будто мы писали ```WITH Position AND WITHOUT Dead```

## Details
Разберем некоторые детали реализации. Парсер можно представить не как один файл с кучей функций, а структуру Parser, в impl которого будут запихнуты основные функции касающиеся парсинга, например подстановка And между With(out), и две стадии парсинга фильтров. пример структуры:
```rust
struct Parser {
    tokens: Vec<Token> // Токены полученные на вход будут хранится тут
}
```

Для первой стадии обработки фильтров не очень подходит текущий enum Filter, ведь для логических операторов он уже требует два других фильтра, потому считаю нужным завести специально для первой стадии enum RawFilter, отличающийся лишь тем что логические операторы будут пустые.  

Примерное содержание impl'а - функция new() - создает новый пустой Parser с вектором обьемом в 12 (В среднем столько токенов и будет, это даже с запасом)
Функция parse(&mut self, tokens: Vec<Token>) -> Vec<ProcessingUnit> точка входа, записывает токены, вызывает другие функции, собирает в юнит и возвращает результат работы парсера. Функция raw_filters(&self) -> Vec<RawFilter> первая стадия сборки фильтров, проходится по токенам циклом и возвращает сырые фильтры. Функция build_filters(&self, raw: Vec<RawFilter>) -> Vec<Filter> вторая стадия собирающая логические блоки.  

Также будут содержатся вспомогательные функции и функция подстановки And между двумя With(out), которая скорее всего будет принимать токены и изменять их внутри Parser.  

Еще будет заведен тип ошибок рядом либо в парсере - ParserError. энам со всеми случаями ошибок, а также будут написаны покрывающие каждый этап тесты.
